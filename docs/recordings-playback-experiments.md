# Playback experiments

`mode` accepts `"playback"` (the default when omitted) or `"download"`. Download mode is a public-portal-derived, unverified recording experiment. Arm it only through the local owner file, for example `{ "mode": "download" }`. Omitting `maxClips` permits unlimited dispatches; an explicit positive safe integer retains a finite budget. No endpoint arms it. Every armed dispatch consumes one slot even on admission failure; it never retries automatically.

Download uses exactly the clip's authenticated record and camera selection, scope, admission gates, live preemption and adjacent selector reservation. It sends outer command 1350, channel 255, header response 0, devType 2 and a fresh segment; inner JSON is `{account_id,cmd:1024,commandType:1024,payload:{cmd:1,backupPath:"",streamId:S,recordIds:[{record_id,download_id,device_sn}],videoQuality:0}}`. `S` is the reserved start selector (6–248); its adjacent selector remains reserved. `download_id` is a unique process-local millisecond timestamp. Quality 0 is fixed experimental input, not a confirmed T9000 capability. There is no time-range variant. Cleanup sends another fresh 1350 segment with `{account_id,cmd:1024,commandType:1024,payload:{cmd:0,cancelId:[{download_id}],backupPath:"abcd"}}` while the original owner remains continuous and inside the cleanup deadline.

Capture ends on a recognized station terminal notification, or at `max(60 seconds, 3 * catalog duration)` after dispatch or 256 MiB of decoded logical FILE-link bytes, whichever comes first, or on cancellation, loss of authority, invalid ingress or storage failure. FILE uses the strict bounded PTCS channel-3 assembler (including real Zstandard decompression), with an 8 MiB frame ceiling. During download capture it also accepts plain XZYH envelopes carrying bit 0x0800, the same station flag quirk as playback. Ordinary FILE and live parsing are unchanged. Cancel is attempted once; every dispatched download then retires the owner through the existing bounded replacement, even if the start send fails or an ACK reports refusal. Admission failure without dispatch does not replace. Cancellation or terminal-looking traffic does not establish release. Replacement may take up to the existing additional 60 seconds. Playback quarantine and live routing remain in force; unexpected playback media is rejected rather than saved as a clip.

Raw reassembled FILE bytes, retaining all inner vendor framing, are written exclusively to `/data/recordings/experiments/<random>.bin` (or the configured recordings root). A matching `.json` contains mode, capture outcome, byte count, scalar download evidence and reconnect outcome. Clear command-1300 envelopes with the existing 22-byte video header are also demuxed to a matching `.h264` or `.hevc` elementary stream when its Annex-B codec is detected. Unknown framing remains available in the raw file. All files use mode 0600 and the directory 0700 on POSIX. Raw writes are independently capped at 256 MiB; evidence files survive cancellation, restart and clip eviction. There is no automatic evidence retention cleanup, so the owner must manage disk usage. Files never enter the clip cache, conversion or HA serving, even if their prefix resembles MP4. The clip terminates with `experiment_only` (or a storage/cancellation reason), never `ready`.

Receipts and diagnostics include `mode`, the normalized experiment and `download`: correlated start/cancel ACK flags and signed status words; cancel attempted/sent; per-link frame counts and decoded bytes with first/last monotonic offsets; bounded link/channel/outer-command route counts; PTCS channel packet counts and native bytes; bounded numeric notification command/subcommand/state/code counts; overflow counts; saved FILE bytes; first/last saved-file-byte offsets, terminal status, parsed video-envelope count, codec, and native-header duration where catalog agreement permits inference; and `firstBytes` classification (`empty`, `mp4_ftyp`, `hevc_annex_b`, `other`). Offsets mark complete logical frame delivery relative to SDK invocation, not first native fragment arrival. No raw prefix or payload identifiers are emitted. `terminalCommandIds` records only cancellation-shaped 1024 notifications or the existing 6001 terminal status vocabulary (2/14, 2/15); these recognized terminal notifications end capture as `eof`, but never prove a complete playable clip or skip cancel/replacement. A plain 1024/code-0 notification without a terminal subcommand does not end capture. Unknown terminal semantics remain inspectable through numeric command/status counts. A signature does not prove a valid or playable file; the portal's worker may be required. The lead must perform any later live testing and offline file inspection separately. These source changes do not update dependency pins or package artifacts.

Local experiment support is inactive unless a regular, valid `experiments.json` exists in the recordings root (default `/data/recordings/experiments.json`). No WebSocket command creates or edits this file. The owner controls arming and removal.

```json
{ "playSpeed": 2, "playType": 1, "clientType": "WEB", "icePolicy": "all", "maxClips": 1 }
```

All keys are optional: defaults are speed 1, type 1, client WEB, unlimited runs, and no ICE override. Unknown keys, wrong types, malformed JSON, files over 4096 bytes, symlinks and unsupported values are inert. Speeds: 1/2/4/8. Type: only 1. Client: only WEB. ICE: relay/all, never host-only. Optional clip budget: integer 1-5; omission is unlimited for either mode. No alternate play type or client value is evidenced by the current source.

Each armed dispatch increments the durable consumed count before the SDK call, including admission failures and station refusals. Armed jobs do not retry automatically. An explicit budget makes the file inert on exhaustion without deleting it; unlimited runs still persist their count across restarts. `experiments-state.json` stores only a digest of the arming generation and the consumed count; restart does not replenish it. A corrupt or unwritable state file refuses overrides. Owner edits or replacement of the arming file create a new generation. One bridge process owns the root; sharing it between processes is unsupported.

ICE is evaluated at **shared RTC session creation**, including replacement, not on an existing session and not at every clip. While armed and any explicit budget remains, new shared sessions use the requested policy. This affects live view as well as playback. No session is forced to reconnect just for an experiment. Existing sessions keep their policy after disarming; subsequent creations return to configured policy (default relay). For a one-clip ICE test, the session must be created while the file is armed, before that clip consumes its slot. `all` permits a direct path but does not guarantee one. Diagnose actual selected local and remote candidate types, not the requested policy.

Always-on diagnostics in `recordings.diagnostics` → `clips.lastJob` / `lastCaptureJob` include scalar timeline offsets, one-second arrival bucket min/median/max, PTCS timing summaries and selected ICE candidate types (or unknown). Offsets share the bridge worker's monotonic start; early media readiness and conversion may precede release/reconnect settlement. Missing milestones are omitted. Ready media remains usable while the bounded station cleanup runs. Experiment receipts record the normalized requested tuple; selected ICE types describe the session actually used.

PTCS exposes a wrapping 16-bit frame sequence and a 32-bit sender clock/frame identifier. Portal headers carry command/segment/channel/selector, not presentation time. The existing shared 22-byte native video-header parser reads a u32 timestamp word at byte 14 and a u16 sequence at byte 6. `nativeFrameTiming` records their deltas and maximum gap in ticks, plus an arrival-spacing comparison explicitly assuming milliseconds. RTC playback units and presentation-time semantics are unverified; constant zero words are observable rather than treated as timestamps. `frameTiming.source=ptcs_sender_clock_unverified` deliberately does not certify presentation timestamps. Its delta, max gap and arrival-spacing comparison are transport evidence; raw header values and packet identities are never retained. Ordinary clip pulls default to speed 2; live view and diagnostic probes retain their existing speed. An ordinary refused or incomplete 2x pull retries once at 1x in the same job after confirmed release or replacement, discarding partial conversion input. Armed experiments retain their requested speed, including 1, and do not retry. `transferSpeed` appears in clip diagnostics and terminal logs. Completeness span, gap, density, cutoff and progress use speed-scaled media time. Accelerated ordinary captures and active EOF experiments prefer a native-header millisecond interpretation only with at least three frames, strictly advancing words, every gap at most 1000 ticks, and inferred duration within 10% (or 250 ms) of authenticated catalog duration (`durationBasis=native_header_experiment`). This is an experimental inference, not protocol validation; `mediaTimestampValidated` remains false. Otherwise accelerated captures use catalog duration (`durationBasis=catalog` normally, or `catalog_experiment` when armed; native duration uses `native_header` or `native_header_experiment`) so accelerated delivery does not shorten MP4 playback. Incorrect catalog duration or a coincidentally matching native clock remains a risk.

After installing the matching SDK and bridge builds, runnable experiments are speed 1/2/4/8 with unchanged type 1 and WEB; relay versus all on a newly created shared session; and passive native-video-header and PTCS-header/arrival-spacing comparison. Existing capture deadlines, 2 GiB aggregate media cap, per-frame limits, wrong-route quarantine and live preemption remain in force. No EOF or unexpected statuses still enter bounded cleanup/replacement. Station support and actual performance require the owner's later live tests. The package dependency pin and installation artifacts must be updated separately before use.
