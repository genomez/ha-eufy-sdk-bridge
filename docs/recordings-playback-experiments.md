# Playback experiments

Local experiment support is inactive unless a regular, valid `experiments.json` exists in the recordings root (default `/data/recordings/experiments.json`). No WebSocket command creates or edits this file. The owner controls arming and removal.

```json
{ "playSpeed": 2, "playType": 1, "clientType": "WEB", "icePolicy": "all", "maxClips": 1 }
```

All keys are optional: defaults are speed 1, type 1, client WEB, maxClips 1, and no ICE override. Unknown keys, wrong types, malformed JSON, files over 4096 bytes, symlinks and unsupported values are inert. Speeds: 1/2/4/8. Type: only 1. Client: only WEB. ICE: relay/all, never host-only. Clip budget: integer 1–5. No alternate play type or client value is evidenced by the current source.

Each armed dispatch consumes one durable slot before the SDK call, including admission failures and station refusals. Armed jobs do not retry automatically. Exhaustion makes the file inert without deleting it. `experiments-state.json` stores only a digest of the arming generation and the consumed count; restart does not replenish it. A corrupt or unwritable state file refuses overrides. Owner edits or replacement of the arming file create a new generation. One bridge process owns the root; sharing it between processes is unsupported.

ICE is evaluated at **shared RTC session creation**, including replacement, not on an existing session and not at every clip. While armed and budget remains, new shared sessions use the requested policy. This affects live view as well as playback. No session is forced to reconnect just for an experiment. Existing sessions keep their policy after disarming; subsequent creations return to configured policy (default relay). For a one-clip ICE test, the session must be created while the file is armed, before that clip consumes its slot. `all` permits a direct path but does not guarantee one. Diagnose actual selected local and remote candidate types, not the requested policy.

Always-on diagnostics in `recordings.diagnostics` → `clips.lastJob` / `lastCaptureJob` include scalar timeline offsets, one-second arrival bucket min/median/max, PTCS timing summaries and selected ICE candidate types (or unknown). Offsets share the bridge worker's monotonic start; early media readiness and conversion may precede release/reconnect settlement. Missing milestones are omitted. Ready media remains usable while the bounded station cleanup runs. Experiment receipts record the normalized requested tuple; selected ICE types describe the session actually used.

PTCS exposes a wrapping 16-bit frame sequence and a 32-bit sender clock/frame identifier. Portal headers carry command/segment/channel/selector, not presentation time. The existing shared 22-byte native video-header parser reads a u32 timestamp word at byte 14 and a u16 sequence at byte 6. `nativeFrameTiming` records their deltas and maximum gap in ticks, plus an arrival-spacing comparison explicitly assuming milliseconds. RTC playback units and presentation-time semantics are unverified; constant zero words are observable rather than treated as timestamps. `frameTiming.source=ptcs_sender_clock_unverified` deliberately does not certify presentation timestamps. Its delta, max gap and arrival-spacing comparison are transport evidence; raw header values and packet identities are never retained. Ordinary jobs retain arrival-based duration. Active EOF experiments prefer a native-header millisecond interpretation only with at least three frames, strictly advancing words, every gap at most 1000 ticks, and inferred duration within 10% (or 250 ms) of authenticated catalog duration (`durationBasis=native_header_experiment`). This is an experimental inference, not protocol validation; `mediaTimestampValidated` remains false. Otherwise experiments use catalog duration (`durationBasis=catalog_experiment`) so accelerated delivery does not shorten MP4 playback. Incorrect catalog duration or a coincidentally matching native clock remains a risk.

After installing the matching SDK and bridge builds, runnable experiments are speed 1/2/4/8 with unchanged type 1 and WEB; relay versus all on a newly created shared session; and passive native-video-header and PTCS-header/arrival-spacing comparison. Existing capture deadlines, 2 GiB aggregate media cap, per-frame limits, wrong-route quarantine and live preemption remain in force. No EOF or unexpected statuses still enter bounded cleanup/replacement. Station support and actual performance require the owner's later live tests. The package dependency pin and installation artifacts must be updated separately before use.
